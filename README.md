# Steady

A beginner-friendly fitness tracker: strength and running plans, workout logging and progress.
It's a mobile-first Progressive Web App that runs in any browser, installs to the home screen,
works offline, and stores all data on the device (no login).

## Run it

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # unit + data-layer tests
npm run build      # type-check and production build (dist/)
```

To try it on a phone on the same Wi-Fi, run `npm run dev -- --host` and open the Network URL.
Installing to the home screen and the camera (Phase 4) need HTTPS, so use a deployed build for those.

## Stack

React + TypeScript + Vite, Tailwind CSS v4, Dexie (IndexedDB), React Router, vite-plugin-pwa, Vitest.

## Project structure

```
src/
  domain/              Pure logic, no storage or UI. Fully unit tested.
    planGenerator/     Rule-based plans from onboarding answers
    runningPlan.ts     Dated running plans toward a goal, and the unrealistic-goal check
    progress.ts        Chart data: strength over time, weekly running, consistency calendar
    exerciseLibrary.ts 45 exercises with step-by-step guides, form cues and substitutes
    exerciseVideos.ts  A short YouTube video demo for each exercise
    records.ts         Epley 1RM and PR detection
    nutrition.ts       Meal math, serving options, barcode normalization, Open Food Facts parsing
    foodSearch.ts      Ranking for the built-in USDA food list
    units.ts, dates.ts, backupReminder.ts
  data/
    db.ts              Dexie schema (all tables exist from v1)
    schema.ts          Record types; every record has id, createdAt, updatedAt, userId
    repositories/      The only code that touches the database. Swap these for a synced backend later.
    backup.ts          JSON export/import and persistent-storage request
    foodSources.ts     Built-in USDA list loader and Open Food Facts lookups (cached)
    seed/usdaFoods.json  13,359 USDA foods and dishes, generated by scripts/build-usda-foods.mjs
  features/            One folder per screen: onboarding, today, session, running, exercises (Exercises tab), meals, history, plan, progress, settings
  components/          Shared UI (buttons, cards, tab bar, difficulty picker, charts)
  theme/tokens.css     Color tokens (dark only for now; a light theme only redefines these)
```

Storage conventions: weights are stored in kilograms and distances in meters, and converted
for display. Dates are local `YYYY-MM-DD` strings. To change the schema, add a new
`db.version(n)` block in `db.ts`; never edit an existing one.

## Build phases

- [x] **Phase 1: Core strength.** PWA shell, onboarding, exercise library, strength plan generation, set logging, rest timer, difficulty and notes, PRs and est. 1RM, export/import
- [x] **Phase 2: Running.** Running plan generation, unrealistic-goal flag, missed-day marking, manual run logging, strength progression suggestions
- [ ] **Phase 3: Progress and Strava.** Charts, consistency calendar and history search are done; Strava connect and import is deferred (see [docs/accounts-and-strava.md](docs/accounts-and-strava.md))

### Phase 1 notes

- Weight-loss and general goals get a mixed plan of strength days plus easy cardio. A running goal without a date gets easy run/walk days; with a date it gets a full running plan (below).
- The first time an exercise is logged sets a baseline. PRs are counted against every earlier completed set, including earlier sets in the same workout.
- The PWA update prompt waits for the user to tap Reload, so an update never interrupts a workout.

### Exercises tab and video demos

- The **Exercises** tab searches all 45 exercises by name, nickname ("RDL") or muscle ("glutes"). Each exercise page has a short video demo (all under 4 minutes) above the written steps, form tips, muscles worked and alternatives.
- Videos come from established sources where possible (physical therapists, hospitals, certification bodies, major fitness channels). All 45 were checked as public and embeddable through YouTube's oEmbed service on October 17, 2026; a test checks every exercise has one. Outside videos can disappear, so recheck them every few months.
- **Privacy:** nothing is requested from YouTube until the user taps Play, and videos play from YouTube's privacy-enhanced player (youtube-nocookie.com). Offline, the player says videos need a connection and the written steps still work.

### Running plans

- **Generated from** goal distance, goal date, experience level and days per week (`src/domain/runningPlan.ts`). Running alone makes every training day a run; with other goals it's 2–3 runs plus full-body strength on the other days, with no strength in the 3 days before the race.
- **Worked backward from the goal date:** peak week 3 weeks out, then a taper (80%, 65%, 45% of peak) into race day, with a rest day before the race.
- **Safe build rate:** no week is more than 10% longer than the biggest week so far, and every 4th building week is an easier recovery week (20% shorter). Tests check this for every distance, experience level and plan length.
- **Sessions:** easy run, long run (Saturday), intervals (experienced and very experienced runners only, with 3+ run days), rest. Hard sessions (long run, intervals, race) are never on back-to-back days. Every session shows a distance or time and a plain-language effort cue.
- **New runners** ("New to exercise") start with 1 minute running / 2 minutes walking, moving to 2/1, then 4/1, then continuous running by week 7. "Getting back into it" starts at 3/1 for two weeks. Run/walk sessions are timed rather than measured.
- **Unrealistic-goal warning:** if the date is sooner than the recommended minimum (5K: 8 weeks new / 4 with experience; 10K: 10/6; half: 14/10; marathon: 20/16), onboarding explains why and offers to move the date. "Continue anyway" builds a compressed plan that still keeps the 10% rule, so it peaks lower, and the plan says so. "Getting back into it" counts as a new runner; custom distances plan like the next race up.
- **Missed days:** any planned session not logged by the end of its day is marked Missed (on app open). It shows in a neutral gray with a dash on Today, the plan and the calendar, with no warnings or streaks. The goal date and remaining sessions don't move. Logging a run later for a missed session marks it done.
- **Run logging** (`/runs/log`): date, distance, time, calculated pace, 1–10 difficulty and notes. Runs show in History with distance and pace; distance and time can be fixed or the run deleted from its history page.

### Progress charts

- **Strength:** per exercise, estimated 1-rep max (Epley, sets of 10 reps or fewer) and top-set weight over time, with the workout's 1–10 rating as a separate small chart underneath (never a second y-axis).
- **Running:** distance per week for the last 12 weeks, and average easy-run pace (easy, long and run/walk runs, weighted by distance).
- **Consistency calendar:** the last 12 weeks, each day completed, missed, planned or rest, each with its own mark (check, dash, outline) as well as color, and the share of planned sessions done (unplanned workouts don't count toward it).
- **Body weight:** a line once there are two entries, with a quick "Log" field.
- Charts are plain SVG (no chart library). Every chart has a hover/tap tooltip and a "Show as table" view. The two strength series use categorical slots 1 and 2, validated together on the card surface for color-vision deficiency and contrast, and are named in a legend.

### Food data

- **Foods and dishes** come from three USDA FoodData Central datasets (public domain), built into the app so search works offline with no API key: **SR Legacy** (7,793 basic foods), **FNDDS** (5,331 foods as people report eating them, like "Burrito bowl, chicken", "Pizza, pepperoni" and "Coffee, latte") and **Foundation Foods** (235 newer lab-analyzed basics not already listed). That's 13,359 foods. Regenerate with `npm run build:foods` (downloads about 13 MB of zips into `.cache/`).
- Search ranks the generic version of a dish first (USDA's "not further specified", shown as "typical"), ignores joining words ("mac and cheese"), maps everyday words to USDA wording ("fries", "soda", "oatmeal"), and picks a sensible default serving (one of the item, a medium or regular size, never "1 miniature" or a single fry). Tests cover about 40 everyday searches.
- **Packaged foods** come from [Open Food Facts](https://world.openfoodfacts.org) (ODbL) by barcode. Its text search is best-effort: the browser-accessible search endpoints are currently blocked or down, so the app says so and points to scanning.
- Logged entries copy the food's name and nutrition, so editing a food never rewrites past days.
- Tracked nutrients: calories, protein, carbs, fat, plus fiber, sugar, saturated fat and sodium. Extras a source doesn't list are stored as missing (shown "–"), never as 0.
- **Suggested targets** (`src/domain/targets.ts`) use Mifflin-St Jeor with an activity factor, a goal adjustment (−15% for weight loss, +5% for strength), a 1,200 kcal / resting-energy floor, protein at 1.2–1.6 g/kg of a BMI-25-capped reference weight, fat at 30%, carbs as the remainder, fiber at 14 g per 1,000 kcal, and limits for sugar and saturated fat (10% of calories) and sodium (2,300 mg). The user reviews and edits every value; nothing is applied automatically.

### Progression (how the 1–10 rating is used)

- When a workout starts, `suggestProgression` (`src/domain/progression.ts`) looks at each exercise's last two sessions and their ratings. If every set hit the top of the rep range and the session was rated 8 or lower, it suggests +5 lb upper / +10 lb lower body (+2.5 / +5 kg), +2 reps for bodyweight moves or +5 s for holds. Rated 9–10, it holds instead. After missed reps two sessions in a row, it offers a 10% drop.
- Suggestions appear as a "Suggestions for today" card in the workout. Nothing changes until the user taps Accept; "Keep current" dismisses it.

### Health considerations

- Optional checklist (in Build my plan and Settings → Health considerations), saved only on the device.
- **Allergies** (dairy, gluten, peanuts, tree nuts, eggs, fish, shellfish, soy, sesame) remove matching foods from every suggestion and meal idea. A test checks that every diet style with any single allergy still has an idea for every meal.
- **High blood pressure** lowers the sodium limit to 1,500 mg; **high cholesterol** lowers saturated fat to 6% of calories (both American Heart Association guidance); **diabetes** ranks high-fiber, low-sugar foods higher. These only steer suggestions; no food is removed.
- **Kidney disease, pregnancy/breastfeeding and a history of disordered eating** switch targets off entirely (like the under-18 block) and clear any saved targets.
- Age uses birth month and year, erring young when the day is unknown, so the under-18 block can't be passed early.

### Navigation requirements

- **Every tracking page that isn't a main tab must have a visible Back or Home action** (`BackButton`). It returns to the previous page when there is one, and otherwise to a named parent page, so a page opened fresh from the home screen or a link always has a way back to Today. A bare `navigate(-1)` is not allowed.
- **Test every new tracking page after entering information:** open it fresh, log or save something, and confirm Back or Home still leads to Today. Then repeat from inside the app and at 375 px wide.
- `src/app.navigation.test.ts` checks every route in `App.tsx` for both rules, so a new page without a way back fails CI. The same requirements are in `CLAUDE.md` for AI-assisted changes.

### Safety limits

- **No nutrition targets under 18.** Calorie and macro targets (suggested or typed in), the plan builder and target-based food ideas require a known age of 18+. Entering an age under 18 clears any saved targets, and `suggestTargets` itself throws for minors as a backstop. Food logging, meal ideas and training still work. Policy lives in `targetsPolicy` (`src/domain/targets.ts`) and every screen reads targets through `useNutritionTargets`.
- Adult calorie suggestions never go below 1,200 kcal or resting energy (Mifflin-St Jeor).

### Plans and recommendations

- **Build my plan** (`/meals/plan`) walks beginners through a few questions and shows suggested targets, how they split across meals, and a sample day of real food. Nothing is saved until the user accepts.
- `src/domain/foodCatalog.ts` holds ~45 everyday foods (keyed to USDA ids, with realistic portion steps and diet tags) and meal templates with plant-based alternatives.
- `src/domain/mealPlanner.ts` sizes portions with bounded least-squares (protein shortfalls weighted most, overshoot cheap), plans days meal by meal so later meals compensate, and ranks food suggestions for the biggest remaining gap with a staple boost and variety across meat, fish, egg/dairy and plant.
- Across 864 simulated days (sex, weight, activity, goal, diet style), the median sample day is within about 2% of the calorie target, and 90% of days are within 6%.
- No external recipe or meal-plan service is used: they need secret API keys (no server here) and have tight free tiers.

### Design

Dark theme built on color tokens in `src/theme/tokens.css` and a small component set in `src/components/ui.tsx` (grouped lists, segmented control, ring and meter). Inter is self-hosted so it works offline. Macro colors are data-viz categorical slots validated for contrast and color-vision deficiency on the app's surface, and always appear next to a text label.

## What Steady does not yet do

- **Strava:** no connection or import yet. It needs a small server to hold Strava's client secret, so it's deferred along with accounts. The design is written up in [docs/accounts-and-strava.md](docs/accounts-and-strava.md).
- **Accounts, sync and friend sharing:** data lives on one device and browser; there's no login, cloud backup or friend sharing (export/import is the backup). Records are already shaped for sync (ids, timestamps, `userId`); the plan is in the same doc.
- **Running plans:** they don't adapt to missed sessions or logged paces (by design, missed days don't shift the plan), there are no pace targets, and the week overview counts timed run/walk sessions by their estimated distance. Free workouts and runs don't get progression suggestions.
- **Packaged-food text search:** depends on Open Food Facts search endpoints that are currently blocked or down for browsers; barcode lookup works.
- **Medical guidance:** health considerations tailor suggestions but aren't medical advice, and age is self-reported, not verified.

## Deploying

The app is a static site. `vercel.json` (Vercel) and `public/_redirects` (Netlify) send all routes to
`index.html`. When Strava and accounts arrive, their secrets go in the backend's environment
variables, never in this repo or the browser bundle.
